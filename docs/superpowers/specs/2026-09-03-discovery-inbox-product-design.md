# DomainHunter 前端产品与界面设计规格

**版本：** 1.0（待开发前评审）
**日期：** 2026-09-03
**读者：** 产品、设计、前端与后端开发团队
**范围：** 本地运行的“发现新网站”审核界面
**替代：** 此文档替代此前以 Queue / Review / Discovery / Ops 四页仪表盘为中心的设计方向。

---

## 1. 一句话定义

DomainHunter 的前端是一个**新网站候选收件箱**：帮助用户在一批经过严格技术筛选的真实域名中，快速理解“它为什么可能是新网站、为什么值得关注”，并做出人工审核决定。

它不是监控大盘、不是数据分析后台，也不是自动发布系统。

## 2. 产品目标与边界

### 2.1 目标

前端必须让一个独立审核者在很短时间内完成以下闭环：

1. 发起一次真实、严格的新网站扫描；
2. 在候选收件箱中优先看到最值得审核的域名；
3. 打开独立详情页，理解其新网站证据、可访问性与产品证据；
4. 批准、暂缓、拒绝或拉黑该候选；
5. 返回收件箱继续处理下一项。

### 2.2 非目标

以下内容不得成为首版主界面：

- 人工生成的 KPI、趋势线或火花线；
- 全量原始 CT 信号与无筛选域名；
- 成本、延迟、预算、工作队列或后台调度控制；
- LLM、CT 日志、筛选阈值等底层运行参数；
- 自动批准、自动发布，或根据前端展示改变候选评分；
- 用 mock、占位成功状态或推测内容替代真实接口返回的数据。

技术诊断、原始日志和运营控制可保留在 CLI 或一个非主导航的诊断入口中，但不属于本设计交付范围。

## 3. 设计原则

| 原则 | 具体要求 |
| --- | --- |
| 决策优先 | 先解释“为什么看它”和“下一步做什么”，再显示技术元数据。 |
| 真实优先 | 每个状态、数字和证据必须来自真实服务数据；未知就显示“未验证”，不补全。 |
| 人审最后 | “高优先级”不等于“已批准”。任何发布性措辞只在人工批准之后出现。 |
| 证据可追溯 | 每个结论可展开到来源、时间、URL 或原始审计记录。 |
| 克制 | 一个主页面、一个详情页、一次扫描入口。避免为后台能力制造独立产品页面。 |
| 可读 | 普通文字使用无衬线字体；仅域名、URL、分数、时间和 ID 使用等宽字体。 |

## 4. 信息架构与路由

首版只有两个主页面和一个弹层/抽屉：

```text
候选收件箱（默认首页）
  ├─ 开始一次真实扫描（弹层）
  ├─ 查看候选列表
  └─ 点击候选
       └─ 候选详情页（独立路由）
            ├─ 打开外部网站
            ├─ 查看证据与原始审计
            └─ 批准 / 暂缓 / 拒绝 / 拉黑
```

### 4.1 页面与导航规则

| 页面 | 用户目标 | 导航状态 |
| --- | --- | --- |
| 候选收件箱 | 查找并选择下一项候选 | 默认首页；顶部显示品牌、收件箱标题与“扫描新网站”按钮。 |
| 候选详情 | 判断一个候选是否值得保留/发布 | 独立 URL；始终有“返回收件箱”。 |
| 扫描弹层 | 发起一次严格的真实扫描并查看真实结果 | 从收件箱打开；完成后返回收件箱并刷新数据。 |

不展示 Discovery、Ops、Analytics 等顶级导航项。若旧链接仍需兼容，可重定向到收件箱或提供轻量说明页，但不能保留为主导航。

## 5. 全局视觉与交互语言

### 5.1 视觉基调

- 页面背景：暖白 `#F7F4ED`。
- 内容卡片：白色 `#FFFFFF`，细边框 `#E1DDD5`。
- 主文字：墨蓝黑 `#17202C`；辅助文字：石板灰 `#5F6B7A`。
- 主操作色：蓝色 `#1769E0`；正向/已验证状态：深青绿 `#007E72`；警告：琥珀色；错误/拒绝：深红色。
- 产品名称、候选名、域名可以大字号突出；不使用霓虹、渐变背景、密集装饰或“终端风”全屏等宽字体。
- 使用系统字体。正文最小 15px，辅助说明最小 12px；所有交互目标最小 40×40px。

### 5.2 顶栏

顶栏高度约 56px，保持简单：

```text
DomainHunter                         候选收件箱         [扫描新网站]
```

- 不显示内部环境名、技术健康点、语言切换、审核人 ID 输入框或全局 KPI。
- 审核人身份在首次执行审核动作时按需询问并在当前浏览器保存，不长期占据顶栏。
- 在小屏幕中，品牌、标题和扫描按钮保留；按钮可仅显示图标加无障碍文字。

### 5.3 通用状态

每个异步区块都必须有四种真实状态：

| 状态 | 视觉与文案 |
| --- | --- |
| 加载中 | 与最终内容相同轮廓的骨架屏，文案“正在读取候选…”。 |
| 无数据 | 明确说明“还没有可审核候选”，并给出“扫描新网站”动作。 |
| 失败 | 说明请求失败，不清空已加载内容；显示“重试”和可复制的简短错误摘要。 |
| 成功 | 仅展示接口确认的结果；不使用模拟计数或假进度。 |

状态不能只依赖颜色，必须同时具备文字和图标/布局变化。所有反馈通过 aria-live 区域播报，且不抢走键盘焦点。

## 6. 页面一：候选收件箱

### 6.1 页面目的

让用户回答：**“此刻最应该审核哪一个真实新网站？”**

### 6.2 桌面布局

```text
┌──────────────────────────────────────────────────────────────────────┐
│ DomainHunter                   候选收件箱             [扫描新网站]   │
├──────────────────────────────────────────────────────────────────────┤
│ 发现了 37 个待审核候选                         [搜索域名或产品]      │
│ 依据：严格新网站门槛已通过；按审核优先级排序                         │
├──────────────────────────────────────────────────────────────────────┤
│ 最高优先级                                                             │
│ ┌──────────────────────────────────────────────────────────────────┐ │
│ │ limitlessrouter.com                         优先审核 · 0.71       │ │
│ │ Limitless Router · AI 基础设施产品                                  │ │
│ │ 新网站：CT 首见 + RDAP 近期注册  ·  可访问：HTTP 200，根域名一致 │ │
│ │ 产品证据：……                                      [查看证据 →]    │ │
│ └──────────────────────────────────────────────────────────────────┘ │
│                                                                      │
│ 其他待审核候选                                                        │
│ ┌──────────────────────────────────────────────────────────────────┐ │
│ │ example.ai · 产品名/未知          优先级 0.57 · 需要更多产品证据  │ │
│ └──────────────────────────────────────────────────────────────────┘ │
│ …                                                                    │
└──────────────────────────────────────────────────────────────────────┘
```

### 6.3 内容规则

1. **标题区**
   - 显示“发现了 N 个待审核候选”。
   - 可选副文案：`仅显示通过严格新网站门槛的候选，按审核优先级排序。`
   - 只提供一个文本搜索框，按域名、产品名和描述过滤当前结果。
   - 首版不提供复杂多维筛选、排序菜单或 KPI 看板。

2. **最高优先级区**
   - 仅展示排序第一的候选，且标题必须是 **“最高优先级”**，不能是“已可发布”或“已验证发布”。
   - 当没有候选时，此区不出现。
   - 当候选不足两个时，“其他待审核候选”区不出现。

3. **候选摘要字段**
   每张卡片最多显示以下信息，缺失字段直接省略，不使用虚构占位值：

   | 字段 | 用途 | 展示规则 |
   | --- | --- | --- |
   | 域名 | 识别候选 | 等宽字体，始终显示。 |
   | 产品名 | 快速理解产品 | 有则显示；没有则只显示域名。 |
   | 审核优先级 | 决定列表顺序 | 显示为 `优先级 0.71`，不渲染仪表盘或分数分解图。 |
   | 结论标签 | 表示模型/规则当前判断 | 如“AI SaaS 候选”“需要更多证据”；不得暗示人工已批准。 |
   | 新网站摘要 | 解释为什么符合项目目标 | 只显示已证实的 CT 首见、注册年龄等事实。 |
   | 可访问性摘要 | 排除跳转到旧站/停放页的误解 | 只显示已证实的 HTTP 结果、最终根域名一致性。 |
   | 一条产品证据 | 帮助用户判断是否值得点开 | 限两行，来自真实证据或产品描述。 |

4. **卡片层级与交互**
   - 最高优先级卡片为整行可点击区域，使用更大字号和更充足留白。
   - 普通候选使用紧凑但非表格化的列表卡片，每项最小高度 96px。
   - 卡片 hover/focus 时出现柔和边框与“查看证据”箭头；不使用整页动画。
   - 点击卡片进入独立详情 URL。浏览器后退必须回到保留搜索词和滚动位置的收件箱。

### 6.4 收件箱状态

| 场景 | 必须展示的内容 |
| --- | --- |
| 首次无候选 | “还没有可审核候选”，解释可启动一次严格扫描。 |
| 搜索无结果 | “没有与‘…’匹配的候选”，提供清除搜索。 |
| 已处理完 | “当前收件箱已处理完”，显示本轮已处理数量与扫描入口。 |
| 列表刷新失败 | 保留旧列表，加顶部非阻塞错误条和重试按钮。 |

## 7. 扫描新网站：收件箱弹层

### 7.1 目的

让用户启动**一次**真实严格扫描，不把底层采集器、模型或阈值暴露给日常审核流程。

### 7.2 弹层布局

```text
┌──────────────────────── 扫描新网站 ────────────────────────┐
│ 将从已配置的真实 CT 来源进行一次严格扫描。                  │
│ 只保留满足新网站、可访问性和根域名一致性规则的候选。        │
│                                                              │
│                              [取消] [开始严格扫描]          │
└──────────────────────────────────────────────────────────────┘
```

首版没有面向普通用户的参数输入。若系统确有安全的“最大探测数”配置，它放进标记为“高级”的可折叠区域，并显示默认值和资源影响。

### 7.3 运行状态与结果

系统不能假装知道服务端尚未报告的阶段。采用下列有限状态：

| 服务状态 | 界面文案与动作 |
| --- | --- |
| 尚未开始 | 显示规则摘要和“开始严格扫描”。 |
| 请求进行中 | 禁止重复提交，显示“扫描正在运行，请保持此页面打开”。不显示伪造百分比。 |
| 完成且有候选 | 显示真实计数：采样信号、通过严格筛选、实际探测、进入收件箱；提供“查看候选”。 |
| 完成但无候选 | 明确写“本次扫描没有产生可审核候选”，并按接口提供的事实区分“未发现新信号”与“信号未通过严格规则”。 |
| 失败 | 写明扫描失败，展示可复制的简短错误摘要和“重试”。绝不显示成功或零候选。 |

扫描完成后关闭弹层并刷新收件箱，或由用户点击“查看候选”再关闭。页面必须显示这次结果来自真实服务返回，而不是浏览器本地估算。

## 8. 页面二：候选详情页

### 8.1 页面目的

让用户在一个独立、安静的页面完成一次人工判断。详情页不再要求用户回忆列表中的信息，也不自动跳转到下一候选。

### 8.2 桌面布局

```text
┌──────────────────────────────────────────────────────────────────────┐
│ ← 返回候选收件箱                                                      │
│                                                                      │
│ limitlessrouter.com                         [访问网站 ↗]             │
│ Limitless Router                                                     │
│ AI SaaS 候选 · 优先级 0.71 · 待审核                                  │
│                                                                      │
│ 为什么它进入收件箱                                                    │
│ ┌──────────── 新网站证据 ────────────┐ ┌──── 可访问与产品证据 ────┐ │
│ │ ✓ CT 首见：…                       │ │ ✓ HTTP：200              │ │
│ │ ✓ RDAP 注册：…                     │ │ ✓ 最终根域名一致          │ │
│ │ ? 未验证项：…                      │ │ 引用的产品证据：…          │ │
│ └────────────────────────────────────┘ └──────────────────────────┘ │
│                                                                      │
│ 产品判断                                                             │
│ 真实产品摘要、来源引用、分类结论与其置信度。                          │
│                                                                      │
│ [查看原始审计数据 ▾]                                                 │
│                                                                      │
│ ┌── 审核决定 ─────────────────────────────────────────────────────┐ │
│ │ [批准]  [暂缓]  [拒绝]  [拉黑]                                   │ │
│ └─────────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────────┘
```

### 8.3 信息模块

页面模块按以下顺序固定排列：

1. **返回与身份**
   - 返回收件箱链接；
   - 域名、产品名（若有）、简短结论标签、优先级、候选版本和当前审核状态；
   - 外部网站链接在新标签打开，并使用安全的外链属性；
   - 域名大而清楚，内部 ID 不作为主视觉信息。

2. **为什么进入收件箱**
   将真实证据整理为两个清晰区块，而非伪造瀑布图：

   | 证据区块 | 可展示事实 |
   | --- | --- |
   | 新网站证据 | CT 首见时间/来源、RDAP 注册年龄或判定、是否符合新网站规则、未知项。 |
   | 可访问与产品证据 | HTTP 状态、最终 URL、最终根域名一致性、页面/产品引用、内部链接（如有）。 |

   每条证据都有：状态（通过/未验证/不通过）、短标题、解释、发生时间或来源。若无来源，不得显示为“已验证”。

3. **产品判断**
   - 一段不超过三行的产品摘要；
   - 当前分类结论，例如“AI SaaS 候选”；
   - 置信度仅在后端确实提供时显示；
   - 所有引用以可点击来源链接或原文摘录呈现；长文本收起。

4. **原始审计数据**
   - 默认折叠；标题是“查看原始审计数据”。
   - 可包含版本、原始证据、事件 ID、技术探测细节和过往决定。
   - 保持可复制、等宽字体、结构化显示；不在初始视图占据空间。

5. **审核决定**
   - 页面底部固定或在桌面右侧停靠，始终容易找到；移动端成为固定底部栏。
   - 主操作：**批准**。其含义是“通过内部人工审核”，不是自动公开发布。
   - 次要操作：**暂缓**、**拒绝**、**拉黑**。
   - 拒绝和拉黑需二次确认；拉黑额外说明其影响范围。
   - 首次操作时要求输入审核人名称/ID。输入成功后本浏览器记住，用户可更改。
   - 操作成功后显示结果摘要，返回收件箱；不自动跳转到另一个候选，避免误操作。

### 8.4 详情页状态

| 场景 | 处理方式 |
| --- | --- |
| 候选不存在或已移出队列 | 显示明确说明、返回收件箱按钮；不能显示旧缓存为当前状态。 |
| 详情数据加载失败 | 保留已加载的身份信息，展示重试；动作栏禁用并解释原因。 |
| 证据不完整 | 展示“未验证”而非留白或正向推断。 |
| 决定冲突 | 显示“此候选已被其他操作更新”，刷新详情并展示最新审核状态。 |
| 操作提交中 | 仅当前动作加载，其他动作暂时禁用，避免重复提交。 |

## 9. 面向前端的最小数据契约

开发团队不应从展示文字、优先级数值或 URL 推断业务事实。服务端应提供以下已归一化的读取模型。字段名称可调整，但语义必须保持。

### 9.1 候选摘要（收件箱）

```ts
type CandidateSummary = {
  id: string;
  version: number;
  domain: string;
  displayName?: string;
  canonicalUrl?: string;
  reviewState: "pending" | "approved" | "deferred" | "rejected" | "blocklisted";
  verdict: {
    label: string;              // 例如“AI SaaS 候选”
    confidence?: number;        // 不存在时省略
  };
  priority: number;             // 排序值，0–1；不等同人工批准
  newness: {
    status: "passed" | "unknown" | "failed";
    summary: string;            // 来自真实 CT/RDAP 结果
  };
  reachability: {
    status: "passed" | "unknown" | "failed";
    summary: string;            // HTTP 与根域名一致性结果
  };
  productSummary?: string;
  updatedAt: string;            // ISO 8601，带时区
};
```

收件箱只显示 `reviewState = "pending"` 的候选。服务端按 `priority DESC` 排序；前端不应私自改写优先级或用任意阈值生成“可发布”分组。

### 9.2 候选详情

```ts
type EvidenceItem = {
  category: "newness" | "reachability" | "product" | "classification";
  status: "passed" | "unknown" | "failed";
  title: string;
  explanation: string;
  observedAt?: string;
  sourceUrl?: string;
  quote?: string;
};

type CandidateDetail = CandidateSummary & {
  evidence: EvidenceItem[];
  audit?: {
    sourceEvents: unknown[];
    observations: unknown[];
    decisionHistory: unknown[];
  };
};
```

`EvidenceItem` 是界面可信度的核心：所有正向表述必须有对应条目；当某项无法获得时，返回 `unknown`，而不是让前端猜测。

### 9.3 扫描与审核动作

```ts
type ScanResult = {
  status: "completed" | "no_candidates" | "failed";
  sampledSignals?: number;
  distinctDomains?: number;
  strictRejections?: number;
  probesRun?: number;
  candidatesCreated?: number;
  errorSummary?: string;
};

type ReviewAction = "approve" | "defer" | "reject" | "blocklist";

type SubmitReviewRequest = {
  action: ReviewAction;
  actorId: string;
  requestId: string;            // 幂等键
};
```

- 扫描结果必须由服务端生成；`failed` 不得降级显示成 `no_candidates`。
- 审核动作必须返回最新审核状态，支持幂等重试，并能表达并发冲突。
- 接口应区分“没有候选”和“扫描失败”。

## 10. 响应式与无障碍要求

| 情况 | 要求 |
| --- | --- |
| 桌面（≥1200px） | 收件箱单列宽内容区；详情页的两组证据可双列并排。 |
| 平板（768–1199px） | 内容保持单列优先，证据区块可按空间折行。 |
| 手机（<768px） | 单列卡片；详情页审核操作固定在底部，次要操作可进入“更多操作”。 |
| 键盘 | Tab 顺序符合阅读顺序；Enter 打开候选；所有审核动作可获得焦点。 |
| 屏幕阅读器 | 使用语义标题、列表、按钮、状态文本和 aria-live，不把关键信息放在纯图形中。 |
| 对比度 | 正文与背景满足 WCAG AA；颜色从不单独承担通过/失败语义。 |
| 动效 | 尊重 `prefers-reduced-motion`；仅在加载、提交和页面过渡中使用短动效。 |

## 11. 文案与语言

- 首版主界面以简体中文为准；域名、外部站点内容和证据原文保持原样。
- 面向用户的术语使用“新网站证据”“可访问性”“产品证据”“优先审核”“待审核”。
- 避免“绝对新”“保证真实”“已可发布”等无法由前端证明的承诺。
- 错误文案必须说明发生了什么、用户可以做什么，且保留可复制的简短诊断信息。

## 12. 验收标准

以下全部满足，首版前端才算完成：

1. 用户打开首页时，能在无需横向扫描表格的情况下识别候选数量、最高优先级候选及其三类核心事实。
2. 候选详情使用独立路由，浏览器返回后保留收件箱搜索和滚动位置。
3. 所有“新网站”“可访问”“根域名一致”“产品判断”陈述都来自服务端明确返回的证据；缺失数据展示“未验证”。
4. 用户能从详情页完成批准、暂缓、拒绝、拉黑；系统要求审核人 ID，防止重复提交，并能反馈冲突/失败。
5. 一次真实扫描的完成、零候选和失败状态在界面中明显不同，且没有 mock 数据、假百分比或伪造成功提示。
6. 用户在桌面、平板和手机宽度下均能阅读并完成主要操作；键盘与屏幕阅读器流程可用。
7. 主导航中不存在 Ops、Analytics 或后台配置页面；所有非审核信息不干扰候选决策。
8. 浏览器控制台没有未处理错误；网络错误不清空已呈现的真实候选。

## 13. 开发交付清单

开发团队应交付：

- 候选收件箱页面；
- 独立候选详情页；
- 扫描弹层及其完成/零候选/失败状态；
- 上述最小数据契约对应的真实接口适配层；
- 搜索、返回状态恢复、审核动作与冲突处理；
- 桌面/平板/移动端样式与无障碍支持；
- 使用真实或可重复的测试夹具进行的端到端验收，不允许以 mock 页面代替真实接口验证。

开发团队不应在未获得新的产品决策前，额外增加运营大盘、图表库、复杂过滤器、多用户管理、自动发布或后台参数配置。
